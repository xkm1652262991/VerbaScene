# 应届生项目面试问答

这份文档不是技术名词清单，而是一套能在面试现场自然说出口的话术。定位是：

- 候选人身份：后端或偏全栈方向的应届生。
- 项目身份：自己真正做过、能运行、能解释取舍的工程项目。
- 表达原则：讲清楚问题、方案和边界，不把单机项目包装成生产级分布式系统。

面试时不要逐字背诵。先记住主线，再根据面试官的追问补细节。

## 一、简历上怎么写

### 项目名称

**VerbaScene（语境片场）—— AI 英语动画短剧生产工作台**

### 一句话介绍

这是一个把创意或已有剧本，逐步变成可编辑剧本、角色和场景资产、视频片段以及最终成片的 AI 内容生产工作台。

### 技术栈

`React + TypeScript + FastAPI + SQLAlchemy + SQLite/PostgreSQL + FFmpeg + Docker Compose`

模型侧采用 Provider Adapter，后台长任务采用数据库持久化的本地任务运行时。

### 推荐简历描述

- 设计并实现剧本、资产、视频制作和导出四个业务模块，支持候选版本、人工采用、局部重生成和完整来源追踪，避免一次生成失败后整条链路重做。
- 将剧本与视频两套内存队列统一为数据库持久化任务运行时，实现任务租约、心跳恢复、资源级去重、幂等提交、取消、有限重试以及父子批量任务。
- 抽象模型 Provider 与媒体存储边界，将异步视频调用拆成提交、轮询、取消和结果获取，任务重启后根据远端任务 ID 继续轮询，降低重复提交和重复计费风险。
- 设计反思式分镜导演 Agent，通过冻结输入、资产检查、独立审稿、一次受限 Patch、检查点恢复和原子保存，将 LLM 输出约束为可编辑、可追溯的分镜批次。
- 使用 Nginx、Docker Compose 和 FFmpeg 完成前后端一键启动与本地数据持久化；当前后端 235 项自动化测试通过，覆盖任务并发、迁移、Provider 合同、Agent 恢复和媒体导出等关键路径。

> 说明：测试数量会继续变化，正式投递简历前应以最新一次完整测试结果为准。

## 二、30 秒开场怎么说

> 我做的项目叫 VerbaScene，是一个 AI 英语动画短剧生产工作台。用户输入创意或者已有剧本，系统会继续完成剧本结构化、角色和场景资产管理、视频片段生成，最后用 FFmpeg 导出成片。这个项目里我重点解决了两个工程问题：一是生成结果不能直接覆盖，要支持版本采用和局部返工；二是模型调用时间长而且可能失败，所以我实现了一套数据库持久化的本地任务运行时，支持恢复、去重、取消和批量任务。现在项目可以通过 Docker 一键启动，但定位仍然是单机工作台，我没有把它夸成分布式生产系统。

这段话说完后停一下，让面试官决定往产品、架构还是任务系统方向追问。

## 三、1～2 分钟项目介绍怎么说

> 这个项目解决的是 AI 视频制作链路比较碎的问题。一次模型调用只能得到一个结果，但真正制作一条短剧，还涉及剧本修改、角色和场景一致性、不同候选版本的选择、单个片段返工以及最后的音视频合成。
>
> 所以我没有把它做成一个输入 Prompt、直接返回视频的页面，而是拆成剧本、资产、视频制作和导出几个模块。生成结果先进入候选区，用户采用以后才成为当前版本；上游内容变化时，只提示下游 Prompt 可能过期，不会自动覆盖用户手动改过的内容。
>
> 后端最重要的一次重构是统一任务系统。最开始剧本和视频各自维护队列，重启恢复、取消和重复提交的处理不一致。后来我把任务状态放进数据库，内存只负责唤醒 Worker。Worker 用租约领取任务，定期心跳；视频 Provider 返回远端任务 ID 后立即落库，进程重启后只继续轮询，不重复提交。项目级批量生成则用一个父任务加多个镜头子任务来汇总进度。
>
> 目前它是 React 加 FastAPI 的模块化单体，默认使用 SQLite 和本地文件，也支持 PostgreSQL 迁移。项目可以用 Docker Compose 一键启动。它还没有鉴权、多租户和分布式 Worker，所以我把它定义为可运行的单机工程项目，而不是生产级 SaaS。

## 四、用 STAR 法则讲项目

### S：当时是什么情况

> AI 视频生成不是一次请求就结束。剧本、参考图和视频都有多个版本，模型调用又可能持续几分钟。如果只用同步接口或者内存队列，服务一重启，任务状态就容易丢；用户重复点击，还可能造成同一个镜头被重复提交和重复计费。

### T：我要解决什么

> 我的目标不是直接上一个很重的分布式框架，而是在单机部署范围内，先把任务状态、恢复、去重、取消和批量生成做正确，同时给未来换成外部 Worker 留出协议边界。

### A：我具体做了什么

> 我统一了任务状态和 Handler 接口，让数据库成为任务真相源；用条件更新和租约实现任务领取与崩溃恢复；用数据库唯一键阻止同一资源的活动任务重复创建；把异步视频 Provider 拆成提交和轮询，远端任务 ID 一拿到就落库；批量生成采用父子任务，子任务独立执行，父任务只负责汇总。Provider 调用期间不保持数据库事务，每个检查点只做短事务写入。

### R：最后得到什么结果

> 最终剧本和视频共用同一套任务运行时，服务重启后可以从检查点或远端任务 ID 继续处理；相同资源不会被并发重复提交；失败、取消和人工重试都有审计记录。项目现在能通过 Docker 一键启动，后端当前 235 项自动化测试通过。真实模型已有短片段和约 32.5 秒的拼接样片，但 1～3 分钟完整成片还没有完成正式验收，所以我不会把它描述成已经生产落地。

## 五、面试官常见问题与回答

### 1. 面试官：先用一句话介绍你的项目

> 它是一个带人工编辑、版本管理和失败恢复能力的 AI 英语动画短剧生产工作台，不是单次调用模型的演示页面。

### 2. 面试官：为什么想做这个项目

> 我发现生成一张图或者一段视频并不难，难的是怎么把多次生成组织成一条可以修改和返工的生产流程。比如角色图换了，不应该把整部短剧全部重做；视频生成失败，也不应该丢掉已经完成的剧本和资产。所以我想做的不只是模型调用，而是模型调用前后的工程系统。

### 3. 面试官：你在项目里主要负责什么

> 我主要负责需求梳理、后端架构、任务运行时、Provider 接入、媒体存储边界、前端任务适配以及 Docker 部署。介绍时我会重点讲统一任务系统，因为这一部分包含并发、事务、恢复和失败语义，是项目里工程含量最高的部分。

如果项目并非独立完成，应按真实情况补充协作者及分工，不要把别人的工作说成自己的。

### 4. 面试官：这个项目和普通的 AI 套壳有什么区别

> 普通套壳一般是把 Prompt 发给模型，再把结果显示出来。我的项目还处理了生成前后的状态：输入快照、候选版本、人工采用、历史版本、局部重生成、任务恢复、重复提交、Provider 差异和最终合成。模型只是其中一个依赖，真正的业务状态仍然由应用自己管理。

### 5. 面试官：完整流程是什么

> 用户先输入创意或导入剧本，系统生成可编辑的英语剧本；然后提取角色、场景和道具，生成并采用参考图；接着拆成多个视频片段，为每个片段编译 Prompt 和引用资产；视频候选生成后由用户选择采用；最后 FFmpeg 按顺序拼接片段，保留原生音轨，并根据选择导出无字幕、英文字幕或双语字幕版本。

### 6. 面试官：整体架构怎么设计的

> 前端是 React，后端是 FastAPI。后端采用模块化单体，按剧本、资产、视频制作和导出拆业务模块；任务和媒体存储放在共享平台层；外部模型放在 Provider Adapter 层。默认数据放 SQLite，媒体放本地目录，Nginx 提供前端静态页面和同源代理，Docker Compose 负责一键启动。

### 7. 面试官：为什么选择模块化单体，没有一开始就做微服务

> 因为现在是单机内部工具，业务量和团队规模都没有证明微服务的必要性。如果直接拆微服务，会提前引入服务发现、网络重试、分布式事务和部署维护成本。我先把模块依赖、事务和接口边界拆清楚；以后真的需要独立扩容任务 Worker 或媒体服务时，再沿这些边界拆出去。

### 8. 面试官：项目里最难的部分是什么

> 最难的不是调用模型，而是处理“模型到底有没有收到请求”这类不确定状态。请求超时不代表 Provider 没接到，如果直接自动重试，可能重复生成、重复扣费。为此我给错误增加了提交状态：明确没提交、已经受理和结果未知。只有明确没提交的可重试错误才自动重试一次；已经受理的继续轮询；结果未知的直接标记人工处理。

### 9. 面试官：为什么不用纯内存队列

> 内存队列实现简单，但进程一重启，队列和正在执行的状态就没了，而且 API 查询到的任务记录可能和实际执行状态不一致。现在数据库保存完整任务状态，内存事件只提醒 Worker 有活要做。即使提醒丢了，Worker 下一轮扫描数据库仍然能找到任务。

### 10. 面试官：你的任务系统是怎么运行的

> 创建任务时先把输入快照和 `queued` 状态写进数据库。Worker 用条件更新领取任务，领取成功后写入自己的租约和心跳。任务执行到 Provider 提交、等待轮询、结果落盘等检查点时，会用短事务更新状态。正常结束后进入成功、失败或取消状态，并释放资源去重键。

### 11. 面试官：什么是租约，为什么需要它

> 租约可以理解为“这个任务在某段时间内归某个 Worker 处理”。Worker 工作时不断续租；如果进程崩了，心跳停止，租约过期后任务才能被重新领取。这样既能恢复崩溃任务，也不会在原 Worker 还正常运行时被另一个 Worker 抢走。

### 12. 面试官：如何保证两个 Worker 不会同时拿到一个任务

> 不是先查询再修改，因为那样中间存在竞态。我使用带状态和租约条件的数据库更新，只有满足条件的那一次更新能成功。Worker 根据受影响行数判断自己是否真正领取到了任务。

如果面试官继续追问数据库差异，可以补充：当前主要验收的是单 API 进程和 SQLite；PostgreSQL 有迁移合同，但多实例并发仍需要单独做压力与故障测试。

### 13. 面试官：资源去重和接口幂等有什么区别

> 资源去重解决的是“同一个项目剧本或同一个镜头，当前只能有一个活动任务”。不管请求来自哪里，只要资源正在生成，新任务就会冲突。接口幂等解决的是“同一个调用方因为超时重发了同一次请求”，相同的 `Idempotency-Key` 会返回原任务。一个约束业务资源，一个识别同一次请求。

### 14. 面试官：为什么把去重放在数据库，而不是代码里先查一下

> 只在代码里先查再创建，两次并发请求可能都查到“没有任务”，然后都插入成功。数据库唯一约束是最后一道并发防线。任务进入终态后会清空活动去重键，这个资源之后才能再次创建新任务。

### 15. 面试官：任务为什么只能自动重试一次

> 这里的任务可能产生费用，盲目多次重试风险比普通接口大。现在只有明确判断请求还没有被 Provider 接受，并且错误可重试时，才自动重试一次。这个次数不是永远正确，而是当前单机内部工具里比较保守的默认值；以后可以按 Provider、错误类型和成本预算分别配置。

### 16. 面试官：Provider 已经接受请求，但服务马上崩了怎么办

> 如果远端任务 ID 已经落库，重启后只继续轮询，不会重复提交。最麻烦的是 Provider 已经接受、但服务还没来得及保存 ID 就崩了，这时本地无法证明是否提交成功。我会把它标成 `provider_submission_uncertain`，停止自动重试，交给人工核对。这比悄悄再扣一次钱更安全。

### 17. 面试官：为什么调用 Provider 时不一直开着数据库事务

> 模型请求和媒体下载可能持续很久。如果一直占着事务，会长时间持有连接和锁，其他请求也容易被拖慢。所以我只在状态检查点短暂开启事务：提交前记一次，返回后再记一次。外部网络等待和数据库事务是分开的。

### 18. 面试官：取消任务是怎么做的

> 还在排队的任务可以直接取消。正在执行或等待 Provider 的任务先进入取消中状态；如果 Provider 支持远端取消，就尽力调用取消接口；不支持时，本地会在下一个检查点停止继续处理，并忽略迟到结果。所以这里是“尽力取消”，不是承诺所有模型请求都能立刻停下来。

### 19. 面试官：批量生成多个镜头怎么设计

> 我创建一个父任务，再给每个镜头创建独立子任务。子任务可以并发执行、单独失败或重试，父任务不直接生成视频，只汇总进度和结果。创建批次时会在一个事务里检查冲突并创建父子任务，只要有一个镜头已经在生成，整批就拒绝，不会留下一半创建成功的脏批次。

### 20. 面试官：为什么重试要创建新任务，不直接把原任务改回排队

> 原任务记录了当时的输入、失败原因和执行轨迹。如果直接改回排队，第一次失败的证据就被覆盖了。新建任务并关联原任务，可以保留完整审计。人工重试默认复用旧输入快照；如果用户想使用最新的镜头内容，就重新调用生成接口。

### 21. 面试官：为什么任务创建时要冻结输入

> 因为任务可能排队几分钟。排队期间用户还可以修改 Prompt 或切换参考图。如果执行时再读取最新数据，用户看到的提交内容和真正生成的内容可能不一致。冻结输入以后，这次任务到底用了什么可以被准确复现和追踪。

### 22. 面试官：为什么剧本并发是 1，视频最多是 2

> 剧本生成会连续经过规划、写作、审稿等阶段，同一个单机进程里并发太多没有明显收益，还可能把文本 Provider 限流打满。视频任务等待时间更长，允许少量并发能提高吞吐，但本地机器、带宽和 Provider 配额都有限，所以目前上限设为 2。这是当前部署条件下的保守值，不是理论最优值。

### 23. 面试官：Provider Adapter 解决了什么

> 不同模型的请求字段、认证方式、轮询状态和能力不一样。如果业务服务直接判断 Provider 名称，代码很快会到处都是分支。Adapter 把这些差异收口，业务层只关心提交请求、查询状态、取消和获取结果。同时能力描述会告诉上层这个模型是否支持参考图、原生音频、智能时长等功能。

### 24. 面试官：为什么异步视频接口要拆成提交、轮询、取消和获取结果

> 如果 `submit()` 内部一直阻塞到视频完成，应用无法及时保存远端任务 ID，服务重启后也不知道该恢复还是重提。拆开以后，提交成功就先落库，后面每次轮询都是可恢复的检查点，取消和带认证下载也有清晰边界。

### 25. 面试官：为什么还需要 MediaStore，直接保存文件不行吗

> Provider 只负责把远端结果安全下载到临时文件，不应该知道项目目录怎么组织。应用再通过 MediaStore 把文件放进最终位置，并生成统一的公开 URI。现在实现的是本地存储，但业务层不再依赖具体路径，以后换对象存储时改动会集中很多。

### 26. 面试官：为什么生成结果要分候选版本和已采用版本

> AI 生成结果不稳定，新结果不一定比旧结果好。如果每次重生成都直接覆盖，用户会失去已经满意的版本。现在新结果先成为候选，用户确认后再采用；旧版本继续保留，方便回退和追踪它来自哪个 Prompt、Provider 和任务。

### 27. 面试官：上游内容变了，下游 Prompt 怎么处理

> 系统会通过输入指纹把下游 Prompt 标记为可能过期，但不会自动覆盖。因为用户可能已经手动优化过 Prompt，自动重编译会把人工修改冲掉。只有用户明确点击重新编译时，系统才生成新的 Prompt。

### 28. 面试官：前端怎么适配后台任务

> 生成接口收到请求后返回 `202` 和任务对象，前端轮询统一任务接口展示排队、执行、等待 Provider、取消中和最终结果。批量视频展示父任务汇总，同时允许查看具体失败子任务。重复提交返回冲突，取消和重试都走统一任务 API，不再由页面维护一套自己的队列状态。

### 29. 面试官：Docker 一键启动具体做了什么

> API 镜像包含 Python 依赖和 FFmpeg；Web 镜像先构建 React，再由 Nginx 提供静态文件，并把 API 和媒体请求同源代理到后端。Compose 配置健康检查、启动顺序、端口和目录挂载。SQLite、媒体和本地 Provider 配置挂载在宿主机，所以容器重启或 `docker compose down` 不会删除数据。

### 30. 面试官：为什么默认只监听本机地址

> 因为项目目前没有登录和权限控制，如果直接监听 `0.0.0.0`，同一网络中的其他人可能访问项目数据和媒体。默认绑定 `127.0.0.1` 是对当前能力边界的保护。以后加入鉴权、受控媒体访问和部署层安全策略后，才能考虑对外开放。

### 31. 面试官：SQLite 数据结构升级怎么保证安全

> SQLite 使用项目自己的增量迁移逻辑，修改旧数据库前会先自动备份；PostgreSQL 使用 Alembic revision。两条迁移路径分开，是因为历史 PostgreSQL 迁移包含数据库专用类型，不能假设能直接在 SQLite 上重放。迁移测试会验证旧项目、任务和资产仍然可读。

### 32. 面试官：你是怎么测试这个项目的

> 我会按风险分层测试。纯业务逻辑和任务状态用单元测试；并发去重、租约、取消和迁移用仓储或集成测试；Provider 使用 Mock HTTP 验证提交、轮询、下载和错误归一化；FFmpeg 用真实本地媒体验证有音轨、无音轨和字幕拼接；最后再做前端构建、OpenAPI 合同和 Docker 健康检查。当前后端全量测试是 235 项。

### 33. 面试官：Mock 测试通过，能说明真实模型可用吗

> 不能。Mock 只能证明应用和 Adapter 遵守约定，不能证明真实账号权限、模型参数、参考图消费、原生音频和下载地址都正常。我把证据分成自动化测试、只读连通、真实生成和完整成片验收四层，介绍项目时会明确自己做到哪一层。

### 34. 面试官：这个项目现在最大的不足是什么

> 第一，没有鉴权和多租户，只适合本机或可信环境；第二，任务 Worker 仍在单 API 进程里，不是经过多实例验证的分布式队列；第三，图片生成和 FFmpeg 导出仍是同步接口；第四，真实 Provider 的完整主链路验收还不够，当前最长真实拼接样片约 32.5 秒，还不能证明 1～3 分钟成片已经稳定生产。

### 35. 面试官：为什么没有现在就做鉴权和多租户

> 因为项目当前目标是先把单人内容生产主链路做正确。鉴权不是加一个登录页就结束，多租户还会影响数据归属、Provider 密钥、媒体访问、任务配额和成本隔离。如果在没有真实多人需求时提前加入，会扩大大量测试面。我已经把它列为共享部署前置条件，但不会为了显得功能多而做一个不完整的版本。

### 36. 面试官：为什么不用 Celery、Redis 或 LangGraph

> 当前只有一个 API 进程，数据库持久化任务加本地 Worker 已经能解决重启恢复和重复提交问题。Celery 和 Redis 更适合真正需要多 Worker、跨机器调度和独立扩缩容的时候。LangGraph 适合复杂、动态分支的 Agent 工作流，但当前流程主要是明确的领域状态和 Provider 调用。工具应该由实际复杂度决定，不是项目里名词越多越好。

### 37. 面试官：如果要支持多人和生产部署，你下一步怎么改

> 我会先做用户、工作空间和项目权限，把 Provider 密钥与租户隔离，并把媒体访问改成鉴权接口或签名 URL；数据库切到 PostgreSQL；任务执行迁移到独立 Worker 和消息队列；媒体换成对象存储；再补配额、成本预算、限流、监控和审计。迁移时继续保留现有任务协议，而不是把业务逻辑重新塞进队列框架。

### 38. 面试官：做这个项目时踩过什么坑

> 一个典型问题是最初把“接口超时”简单当成“提交失败”。后来我意识到，外部 Provider 可能已经收到请求，只是响应没有回来。如果自动重试，会造成重复任务和费用。这个问题让我把错误是否可重试、Provider 是否已受理和任务业务状态分开建模，也让我更重视外部调用前后的检查点。

也可以根据真实经历讲 Docker 环境变量解析、非 ASCII 路径构建或前后端任务合同适配，但只选择自己能继续解释代码细节的一件事。

### 39. 面试官：你在项目里怎么使用 AI 编程工具

> 我会用 AI 帮助检索代码、比较方案和生成重复性实现，但需求边界、数据模型和失败语义需要我自己确认。生成的代码不能直接算完成，我会看调用链和事务边界，再用定向测试、全量回归和真实容器启动验证。比如任务系统里“未知提交不能自动重试”就是业务判断，不是让工具随便补一个重试装饰器。

不要回答“项目都是 AI 写的”或“AI 只负责查资料”。如实说明它参与了什么，以及你如何对结果负责。

### 40. 面试官：怎么证明这个项目真的是你做的

> 我可以现场从一个具体故障讲完整链路。比如同一个镜头被重复点击时，请求如何进入任务创建、数据库唯一约束怎样拦住并发、前端如何收到冲突；或者服务在视频提交后重启时，远端任务 ID 保存在哪里、Worker 为什么只轮询不重提。能从页面、API、数据库一直讲到失败恢复，比背技术栈更能证明我真正做过。

### 41. 面试官：这个项目有什么量化结果

> 目前我能确认的工程数据是后端 235 项自动化测试通过、Docker PostgreSQL/API/Web 三容器配置校验通过，以及已有约 32.5 秒真实拼接样片。由于还没有正式用户量、稳定生成成功率和完整成本记录，我不会编造节省百分比。下一步会制作 60～90 秒原创验收样片，并记录每个任务的耗时、失败原因、重试次数和成本，再形成可信指标。

### 42. 面试官：如果再给你一周，你最先做什么

> 我不会先加更多 Provider。我会先完成一条 60～90 秒原创短剧的真实主链路验收，记录成功率、耗时、成本和一次局部返工。这样能先验证现有架构是否真的解决用户问题，也能暴露最值得修的失败点。确认单人链路稳定以后，再决定优先做异步导出还是鉴权。

## 六、面试官可能故意压你的问题

### “你这个任务系统不就是自己造了一个低配 Celery 吗？”

> 可以这么理解，它解决的是任务持久化和恢复中的一小部分问题，但我没有把它当成 Celery 的替代品。当前目标是单进程、零额外基础设施，所以我只实现了当前确实需要的租约、去重、取消和父子任务。需要多机器调度、消息确认和成熟运维能力时，我会迁移到专业队列，并复用现在的任务业务协议。

### “既然没有用户，这个项目有什么价值？”

> 它现在的价值主要是验证产品流程和工程方案，还不是商业结果。我通过它解决了长任务恢复、AI 结果版本管理和多 Provider 边界这些真实问题。没有用户数据的部分我不会包装；如果继续推进，下一步就是用完整样片和小范围真实使用来验证价值。

### “你写了这么多状态，会不会过度设计？”

> 如果只是一次同步生成，确实没必要。但视频 Provider 本身就是异步的，排队、已提交待轮询、等待子任务和取消中的处理方式不同。把它们都压成“处理中”，重启和取消时反而需要猜测。我只保留会改变系统行为的状态，没有为展示好看增加无业务含义的状态。

### “为什么不用一个大 Service 全部写完？”

> 早期集中写确实更快，但后来视频生成同时负责请求编译、Provider 调用、候选保存和批次协调，修改一个环节容易影响其他环节。我按变化原因把它们拆开，同时保留模块化单体部署，没有为了拆分而增加网络调用。

### “你说支持 PostgreSQL，那线上跑过吗？”

> PostgreSQL 目前完成的是 Alembic 迁移合同和代码兼容，不代表多实例线上验证。当前真实运行目标仍然是 SQLite 单机模式。如果岗位需要，我可以继续补 PostgreSQL 集成环境、并发压测和故障恢复测试，但不会把迁移脚本通过说成线上跑过。

## 七、哪些话不能说

| 不建议说 | 建议说法 |
| --- | --- |
| 我做了分布式任务系统 | 我做了面向单 API 进程的数据库持久化任务运行时 |
| 支持所有主流大模型 | 通过 Adapter 接入多种 Provider；真实验收状态分别记录 |
| 已经生产级可用 | 已完成单机工作台和自动化验证，生产能力仍有明确缺口 |
| 实现了多 Agent 自动创作 | 当前采用领域服务和显式状态；没有使用 LangGraph |
| 项目能稳定生成 1～3 分钟成片 | 目标规格为 1～3 分钟，当前最长真实拼接证据约 32.5 秒 |
| 使用 Redis 做任务队列 | 当前数据库是真相源，Redis 不是任务队列 |
| 支持多人协作 | 当前没有鉴权和多租户，只适合本机或可信环境 |
| 测试都过了，所以真实模型没问题 | Mock 合同通过和真实模型验收是两个结论 |

诚实说清边界不会减分。应届生真正容易失分的是概念说得很大，但一追问就对不上代码。

## 八、现场演示建议

如果面试官允许演示，控制在 3 分钟内：

1. 用 `./docker/up.sh` 展示一键启动和健康状态。
2. 打开一个已有项目，说明剧本、资产和视频制作三个工作区可以自由进入。
3. 展示一个候选版本如何被采用，以及历史版本没有被覆盖。
4. 提交一个 Mock 视频任务，展示任务状态和重复提交冲突。
5. 在任务中心展示父子关系、错误和重试入口，并说明任务接口保存了输入快照。
6. 最后展示导出配置或已有样片，不在现场调用付费、耗时的真实视频模型。

演示的目的不是把所有页面点一遍，而是证明“页面操作背后对应着你刚才讲的状态和数据设计”。

## 九、最后的收尾话术

> 这个项目让我学到最多的不是怎么接一个模型，而是怎么处理外部系统的不确定性，以及怎么在功能、复杂度和当前阶段之间做取舍。现在它还有鉴权、分布式执行和完整真实样片这些缺口，但这些边界我都能说清楚。如果继续做，我会先用真实数据验证主链路，再决定下一步工程投入。

这句话的重点不是“项目还不够好”，而是让面试官看到：你知道自己做成了什么，也知道下一步为什么这样排。

## 十、面试前检查清单

- 确认最新测试数量，不背过期数字。
- 准备一个最熟悉的任务恢复故障案例。
- 准备一个自己主动放弃的方案，例如当前没有引入 Celery 或多租户。
- 能画出前端、API、任务运行时、数据库、Provider 和媒体存储之间的关系。
- 能解释幂等与资源去重、失败与未知提交、候选与采用版本的区别。
- 只陈述真实做过的 Provider 和样片证据。
- 不编造用户量、成功率、节省时间或成本数字。
- 本地提前执行一次 Docker 启动，不在面试现场临时安装依赖。
