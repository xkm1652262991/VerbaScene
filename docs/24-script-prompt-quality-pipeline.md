# 剧本与生成 Prompt 质量流水线

## 1. 目标

剧本质量不能继续依赖一条不断加长的总 Prompt，也不能用字数、字符数、场景数或固定句数冒充质量。

本项目将剧本生成改为可追踪的创作流水线：

```text
项目输入
  -> 创建持久化剧本任务（queued）
  -> Story Architect（StoryBlueprint）
  -> Script Writer（ScriptDraft）
  -> Comprehensive Reviewer（ScriptReview）
  -> 必要时 Targeted Reviser（ScriptPatch）
  -> 确定性合同校验（ContractReport）
  -> 原子保存剧本版本与任务结果
  -> 资产提取与分镜
```

模型负责创作判断，程序只保留下游确实需要的最小合同。程序不得因为文本长短、字段字数或审美分数拒绝一份剧本。

## 2. 设计原则

### 2.1 创作质量与技术合同分开

- 创作质量：人物欲望、具体阻碍、因果、信息增量、情绪兑现、对白意图、英语自然度和可表演性。
- 技术合同：响应能解析为对象、至少有一个场景、场景有可见动作、对白能绑定角色和场次。
- 只有技术合同失败才阻止保存；审美问题进入审稿意见或定点修订，不伪装成格式错误。

### 2.2 不使用长度代理指标

- 不按输入字数猜测成片时长。
- 不按 Prompt 字符数报警或截断创作信息。
- 不要求固定台词字数、句数、场景数或机械重复次数。
- 时长只作为叙事密度与后续视频片段规划的参考，不作为剧本文本长度公式。

### 2.3 A1 不等于幼稚或机械

- 简化词汇和句法，不简化人物意图与因果。
- 每句英文对白必须承担真实交流功能，例如请求、拒绝、确认、提醒、发现或情绪反应。
- 目标表达可以自然复现，但复现时情境或交流功能必须变化。
- 能由动作表达的信息不让角色口头讲解。

### 2.4 审稿不自动统一审美

审稿输出统一为 `issues`。每项包含 `category`、`severity`、`scene_nos`、证据、修复指令和受保护元素：

- `category`：`causality | character | dialogue | continuity | production`。
- `must_fix`：因果断裂、导入事实被篡改、角色行为无动机、结尾不兑现、无法动画化、连续性冲突、对白不自然或教学表达破坏交流。
- `editorial_note`：节奏、趣味、风格和可选增强建议。

只有 `must_fix` 触发一次 `ScriptPatch`；`editorial_note` 不自动改稿。英语质量属于 `dialogue`，不再设置独立英语教练。

## 3. 故事开发合同

故事开发阶段只决定故事，不编写完整生产场景。输出包含：

- `premise`：本集最小故事承诺。
- `theme` 与 `opening_hook`：故事主题和开场抓点。
- `dramatic_question`：开场建立、结尾回答的问题。
- `emotional_payoff`：结尾给观众的情绪或认知兑现。
- `protected_requirements`：用户明确要求保留的事实、关系、结局与表达。
- `language_opportunity`：故事自然需要的英语交际功能与候选表达；不是强制课堂练习表。
- `characters`：主要人物在本集想要什么、为什么行动。
- `beats`：按因果排列的事件变化；每个节拍说明可见事件、人物选择或反应、产生的新状态。
- `continuity_facts`：不可无因改变的人物、道具、地点和关系事实。
- `creative_risks`：容易写成说教、重复、无动作或模板反转的位置。

AI 创意模式允许围绕创意补足完整因果；导入模式必须把原文事实、人物关系、结局和对白意图视为上限约束。

## 4. 生产剧本合同

`scenes` 仍是下游唯一真相源，但 Prompt 不再把所有字段都描述成同等重要的格式任务。

每场的核心信息是：

- 本场发生了什么可见变化；
- 为什么由上一场导致；
- 进入与离开时人物、道具和环境分别是什么状态；
- 谁在场、谁说了什么、台词承担什么意图；
- 哪些声音与可见动作同步发生。

地点、时间、人物、道具、情绪、来源依据和连接动作继续保留，用于资产、分镜、连续性和审计。缺少非核心描述时由归一化层使用空值，不要求模型为了填表编造内容。

## 5. Provider 消息边界

- 编剧职责、质量优先级、数据安全和阶段边界放在真正的 `system` 消息中。
- 用户创意、导入正文、项目设置、故事蓝图、草稿和审稿意见以 JSON 数据放在 `user` 消息中。
- 用户原稿属于待处理内容，不得覆盖系统职责或输出合同。
- 可配置 Prompt 作为系统策略补充，不再与用户输入拼成一段无法区分角色的文本。

## 6. 视频 Prompt 编译

视频 Prompt 采用镜头优先结构，不按字符数截断：

1. 一句任务说明和真实参考绑定。
2. 直接按“镜头1、镜头2……”排列内部镜头。
3. 每个镜头包含可见动作、对白和同步音效。
4. 末尾保留连续性、音频和画面禁止项。

编译器必须：

- 只使用 Provider 实际能识别的素材编号，不把内部 `@资产名` 当成模型引用；
- 只绑定实际参与当前镜头且确有参考图的角色、场景和道具；参考图已定义外观时不复制数据库字段；
- 不把未在动作中使用的道具塞入 Prompt；
- 规格和时长由 Provider 参数承载，不在创意 Prompt 中重复；
- 保留用户手工编辑稿，只有显式重新编译才覆盖；
- 不用“Prompt 太长”作为质量问题，真正的问题应描述为矛盾、重复、素材错绑、不可执行运镜或多个动作峰值竞争。

## 7. 失败与降级

- 故事开发失败：使用输入事实构造中性蓝图，继续尝试写稿，并在任务轨迹中记录降级。
- 初稿结构无法解析：额外执行一次“内容保持不变的结构恢复”，不让格式指令污染正常写作 Prompt。
- 审稿失败：保留已可用初稿，记录审稿不可用，不因辅助阶段失败丢弃作品。
- 修订失败：保留修订前初稿，并记录失败；不得用失败修订覆盖可用稿。
- 每次生成最多自动修订一次，避免审稿器循环改写并抹平风格。
- `ScriptPatch` 只能替换审稿点名的场景；重复、未知或越权场号会使整个 Patch 无效，未点名场景保持原值。
- 审稿或 Patch 降级不会被记为质量通过：任务以 `quality_gate=review_unavailable` 或 `needs_attention` 明确暴露。

## 8. 质量数据

每次任务记录：

- 流水线版本、Provider、模型和分阶段参数；
- 故事蓝图、初稿、统一问题清单、可选 Patch、合同报告及最终稿；
- 解析恢复或降级原因；
- 用户后续保存的场景稿和最终采用结果。

后续建立固定回归集与人工 A/B 选择。模型评分不作为唯一验收，也不因一个总分自动拒绝剧本。

## 9. 硬切后的模块边界

剧本质量链路不得再集中到一个不断增长的 Agent 文件中：

- `script_prompts.py`：只负责阶段 Prompt 和 system policy，不解析响应、不访问数据库。
- `script_contracts.py`：只负责故事蓝图、审稿对象、用户明确短语和最低内容合同。
- `script_screenplay.py`：只负责生产场景解析、归一化、可读剧本渲染和对白派生。
- `script_pipeline.py`：只负责阶段顺序、Provider 调用、降级策略和可恢复检查点。
- `script_service.py`：只负责创建任务、保存剧本版本和项目状态。
- `script_generation_queue_service.py`：只负责后台排队、取消、重启恢复和工作线程。

前四个创作核心模块不得导入 ORM 模型、数据库 Session 或表结构。`script_service.py` 在应用边界把当前持久化记录翻译为不可变的 `ScriptGenerationInput`；以后无论改为项目文件、文档数据库还是重新设计的多智能体关系模型，创作核心都不随之改写。

旧的 `build_script_adaptation_prompt` 入口和 `script_development.py` 聚合文件直接删除，不保留同名转发壳。调用方必须迁移到新合同，避免两套路径长期并存。

## 10. 持久化队列与恢复语义

`POST /api/projects/{project_id}/script/generate` 返回 `202` 和已持久化的 `GenerationTask`，不在 HTTP 请求中等待多次模型调用。前端轮询任务状态，成功后读取最新剧本。

每个成功阶段都把结构化检查点写入 `GenerationTask.raw_response.checkpoint`：

- `blueprint`
- `draft`
- `review`
- `patch`（仅发生修订时）
- `contract_report`
- `final`
- `quality_gate`
- `pipeline_trace`

服务重启时，仍为 `queued` 的任务重新入队；处于 `running` 的剧本任务退回 `queued`，增加恢复次数，并从最后一个完整检查点继续。已完成阶段不得重复付费调用。最终剧本与任务成功状态在同一数据库事务保存，避免产生“有剧本但任务失败”或“任务成功但无剧本”的半成品。

当前实现是单进程本地工作线程，不冒充 Celery 或分布式队列。多实例部署前必须换成具备租约和跨进程互斥的外部队列。

写作阶段读取 `script_rewriter` Agent 配置，审稿阶段单独读取 `script_reviewer`。两者可以配置不同 Provider、模型、system policy 和温度；未配置 `script_reviewer` 时才明确回退到写作模型。任务检查点记录每个阶段实际使用的 Provider 与模型，不能把“不同 Prompt”误报成“异构评审”。

V3.1 是唯一可执行的创作链路：

- 审稿产物只接受 `issues`；不再接受或写出旧 `must_fix` / `editorial_notes` 数组，也不保留重复的 `verdict` / `summary` / `strengths` 外壳。审稿是否可用由流水线状态记录。
- 修订阶段只使用 `script_patch` 和 `patch_applied`，旧 `script_revision` / `revision_applied` 不再读取或写出。
- 任务结果不再投影 `review_verdict`、`must_fix_count`、`unresolved_must_fix_count` 和 `final_contract_review`。
- V3.1 之前未完成的 checkpoint 不恢复旧阶段，会按新版本重新开始；已完成历史任务只允许界面只读展示，不能反向驱动新链路。

## 11. 退出决策的质量代理与数据库后置

- `Chapter.source_word_count` 暂时保留为旧数据与旧客户端的兼容元数据，但编剧、审稿、时长规划和质量判断不得读取它。
- 本轮不新增删列迁移，也不为了当前流水线调整关系表；数据库结构等多智能体角色、产物和协作关系稳定后统一设计和迁移。
- `scan_avd_prompt(max_chars=...)` 的兼容参数删除。
- Prompt 治理中的 `_bounded_join(..., max_chars=...)` 删除，改为不裁剪语义信息的去重合并。
- 不保留仅为旧测试或旧调用方存在的 Prompt 函数别名。

标题长度、主键格式、Provider 真实素材数量上限等技术边界不属于创作质量代理，仍由 API 或 Provider 合同负责。

当前可变的协作状态放在 `GenerationTask.raw_response.checkpoint` 中，并带流水线版本、阶段名、实际 Provider/模型和阶段产物。未来增加策划、编剧、对白润色、连续性审校等智能体时，先用版本化产物协议验证角色边界；只有查询、并发、审计或复用需求稳定后，再把确有价值的对象提升为正式关系模型。任务 JSON 是演化缓冲层，不应成为永久无结构数据仓库。

## 12. 固定回归集

仓库内维护不少于 30 个剧本难例，至少覆盖：

- 明确英文短语不可遗漏；
- 导入稿事实、关系与结局不可篡改；
- 多人物对白归属与角色差异；
- 道具持有、地点和时间连续性；
- A1 自然交流而非课堂操练；
- 无对白、低冲突、情绪型和喜剧型故事；
- 输入中的 Prompt 注入文本不得改写系统职责；
- 长输入不得因字符阈值被截断。

离线评测只判定可客观验证的合同；叙事趣味、节奏和情绪兑现使用匿名成对人工选择。真实 Provider 批量评测必须显式开启，默认命令不得产生模型费用。
