# 资产管理

## 资产目录

资产库按角色、场景和道具分类。角色与场景展示：

- 基础形象 `base`
- 剧情状态变体
- 图片 Prompt
- 当前版本
- 历史版本
- 待采用候选
- 出现场次

不使用自由拖拽节点画布。

道具仍在目录中展示名称、状态、剧情作用和出现位置，但默认不提供独立图片生成。

## 状态变体

每个 `state_variant` 必须有稳定 `key`，但它是否对应独立图片由实体类型决定：

- 角色只有 `base` 多视角设定图。剧情状态变体是 Prompt 数据，不创建独立图片槽位。
- 场景的昼夜、季节、破损等持续视觉变化可使用不同 `variant_key`，同一状态的重新生成只递增版本。

## 候选与采用

模型输出先写入 `AssetCandidate`。用户采用候选后创建正式 `Asset` 并切换该版本键的 `is_selected`。历史资产不删除。

采用只表示“后续默认引用这个版本”，不表示阶段审核，也不会解锁页面。

## 视频参考素材策略

视频请求默认只按显式绑定顺序选择最多 2 个角色版本和 1 个场景版本。片段首帧不会
自动进入请求；用户明确启用后才增加为第一张图片。角色多角度源图和道具图不作为
视频参考。这样保留必要的一致性控制，同时避免过多图片造成主体、风格和特征优先级冲突。

## 过期提示

上游修改后保留原资产，并在视频 Prompt 或成片元数据中记录可能过期。用户决定继续使用、切换版本或重新生成。

## 服务边界

资产服务按稳定生命周期分层，不再把查询、文件、生成和候选采用写在同一个服务中：

- `asset_repository.py`：资产查询、当前链过滤、版本号和来源追踪。
- `media_storage_service.py`：本地媒体路径、Data URI 落盘和文件清理。
- `media_generation_support.py`：图片和视频共用的任务、进度、审计和错误归一化。
- `asset_lifecycle_service.py`：上传、选择、删除、抽帧和采用后副作用。
- `image_generation_service.py` 与 `video_generation_service.py`：分别拥有各自的 Provider 编排、重生成和结果持久化。
- `asset_candidate_service.py` 与 `asset_resolver_service.py`：继续独立负责候选版本和生成引用解析。

`asset_service.py` 只是兼容旧导入路径的薄门面，不实现业务函数。项目内部调用方必须直接依赖实际拥有者，不得从其他服务导入下划线私有函数。

依赖方向固定为：存储/仓储/任务支持 → 资产生命周期和图片/视频生成 → API 路由与队列。图片与视频生成模块不相互导入，也不依赖兼容门面或候选服务。

入口服务保持现有事务边界；底层 repository 和 storage 辅助函数不主动 `commit`。本拆分不改变 HTTP 合同、数据库结构、Provider 参数、候选优先或历史版本保留规则。
